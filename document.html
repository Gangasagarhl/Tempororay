SSD failure analysis: from files in a folder to a test script

When a solid-state drive (SSD) fails, an engineer must find out why, and must be able to make the failure happen again. Today that means reading very large recordings by hand. This system reads the recording, finds the errors with fixed code, and produces a test script that replays the failure. AI agents do the drafting, so less human work is needed. A named person, the admin, approves every important step. AI reduces human work here; it does not replace the admin.

Be aware. Every recording on this machine is synthetic. None came from a real drive or from the field. No real drive has run a generated test: they ran on a simulated drive. The scorecard at the end says what that means for each claim.

Conversations that are kept, and compacted at 95 %

Every agent has a conversation. Over the Model connection, an agent that is asked again in the same run (the Coder's next round, an agent asked again after the admin's comments, a chat) is sent its earlier questions and answers before the new question. What was sent before is read from the model service's cache. Every turn is written to disk: the question as sent, the answer, the seconds it took and the service's own token count. After a restart the conversation comes back. A step that is run again with the same question, word for word, does not send it twice.
Compaction. A model reads a limited amount of text at once. When a conversation and its next question would fill more than 95 % of that (and never so much that a full answer no longer fits), the model writes a summary of the conversation: the task, what is settled, the exact names and numbers, the state of the work, what is open and what was ruled out. The conversation is closed and kept to read, and it goes on as its next part from the summary and the last two turns word for word. The share can be changed (agentic.compact_at in the configuration file). The same rule holds for a terminal session.

After the data: your questions, and stage 2 as a choice

When Family 1 has finished the last data dictionary, the flow stops at one card. Nothing after it starts until the admin decides there.

Ask all the Managers. The admin writes what to look for, for example “is there any command that timed out in this data?”. The Admin Agent puts the question to the Manager of every file at the same time. A Manager only names columns and keywords. Program code checks each name against that file's data dictionary, drops a name that is not there, and takes the row counts and the line numbers from the dictionary. The answer is Yes, present (a Manager said yes and a name it gave is in the data), No, not found (every file was read and every Manager said no) or Cannot tell. A dictionary keeps keywords and the most frequent values, not every number, address or identifier, so a question about one exact value is answered “cannot tell”, and the answer says so.
Read the new files. If the data is not there, the admin puts the CSV file that holds it into the folder and presses this button. Only the files that were not read get the three agents of Family 1. Files already read are not read again. The card then comes back.
Stage 2 is a choice. The tree is not needed for every input. The card says, counted by program code:
  • what the tree is needed for: a rule that looks at more than one file at once, the error rules of the detector, and the isolation of a defect;
  • which of the analyzer's five exports the folder holds, and which other CSV files;
  • whether the fixed joining strategy can build these files, and the reason when it cannot;
  • whether a tree of these same files was built before (it is then used again);
  • how many items of the rules library read the tree, and how many read one file.
The fixed joining strategy was written for the analyzer's five exports. It is an option, never a condition. The admin presses Go to stage 2 (Family 2 builds the tree with it) or Go on without stage 2 (Family 2 is skipped and the rules read the CSV files as they are). The button for stage 2 is off when the strategy cannot build the files. Without a tree, an item that reads the tree cannot run: the plan of Family 3 shows it as blocked with the reason, never ticks it, and refuses it if it is sent anyway.
Any CSV files. A folder no longer has to hold the analyzer's exports. Every CSV gets its data dictionary. A rule on such a file is kept in a sixth group of the rules library, Other CSV files; its procedure names the file by its own name (a plain file name, never a path), and Family 4 writes its code for that file. Every kind of data the rule needs goes to the Manager of every file, as on the card after Family 1: a Manager only names columns and keywords, the code checks each name against the data dictionary, and the row counts and line numbers come from the dictionary. The card shows each kind of data as
  • found: the file and the column, how many rows hold it and on which lines to see it;
  • not found in any file: put the CSV file that holds it into the folder and press Read the new files on the card after Family 1 (the analysis can be opened again at stage 1 for that). The requirements cannot be approved while a needed kind of data is not found, unless the admin writes in words why to go on;
  • cannot tell: it needs the admin's tick “go on with the open points”.
A name the model invents is dropped and never counts as found. Family 2 is asked only when the rule reads the tree: if no tree was built for the analysis, the card says so, and the requirements cannot be approved.
3. The rounds: code, test, code, test. At most 10 rounds; the admin can set 1 to 20 in Settings or on the requirements card. In each round:
  • the Coder writes or revises the code, at the model's highest effort setting, and keeps notes of what it understood and decided;
  • the program checks the code (it compiles, it imports only what is allowed, it defines the one function that is run), runs it on the first 200 records of the real files, and runs every small data set made so far;
  • the Tester reads the code against the procedure and makes new small data sets, each with the output it expects, to find an input on which the code is wrong;
  • what failed goes back to the Coder, and the next round starts.
The rounds end on a clean round (the program's checks pass, the run on real records passes, every data set passes or was withdrawn or set aside, and the Tester added no failing data set and no remark), or when the rounds are used up, or when the Coder returns the same code and objects to nothing, or when the run is stopped. Generated code runs only in its own process, with a memory and time limit and access to its own files only. Nothing a model wrote runs inside the application.
Since 14 November 2026 the family is “Family 4 · Coding research”: it researches the data first, and proves each requirement on the data at the end.
  • The data research step comes before the requirements and has no card of its own: its record opens the requirements card, surprises first. It gathers what the other families hold: Family 1's whole data dictionary of every file the rule touches, Family 2's joining facts, and everything the admin said about the rule in Family 3, dated. Then program code reads each touched file once, whole, and measures the columns the rule touches: every spelling of “nothing” with its count, numbers stored as text, the most frequent values, and where the rule's own words are stored in the data (the column, the exact spelling, the count, or “in no column” with the nearest spelling).
  • Conflicts are found by program code, not by a model: the rule against the data, the dictionary against what was measured, two answers of the admin. A measured count goes before a description, and the admin's latest answer before an earlier one. A conflict between the rule and the data becomes a question to the admin.
  • The requirements are numbered (R1, R2, …). Every decision the rule leaves open (empty cells, ties, empty groups, a value exactly at the limit, units) becomes a requirement or a question; nothing is assumed in silence.
  • The whole file, and an accounting. After a round whose small data sets pass, the program runs on the whole real file and says how many rows it read, kept, left out for which reason, and could not evaluate. Program code counts the rows itself and checks that every row is accounted for exactly once.
  • A table per requirement on the code card, “not met” first: its checks, the rows that show it, and a verdict decided by program code: met, not met, not exercised (its condition never occurred in the data) or could not be checked. There is no overall percentage. The admin decides each open requirement; nothing is chosen for them.
  • A check must be able to fail. For each data set the Tester says what a program that ignored the requirement would give, and program code confirms the two results differ. A data set that cannot tell the difference is marked as not testing that requirement.
Measured with the real model (claude-sonnet-5-5, a CSV of 300 rows; the rule said “timed out” and 43 ms, the file said “timeout” and held microseconds): the research took 8.5 seconds and found both conflicts, the empty cells, the 4 “N/A” and the 5 numbers written with a separator. After the admin's answers there were 15 requirements. On the whole file every one of the 300 rows was accounted for (19 kept, 281 left out with their reasons); 13 requirements were met, 2 could not be checked and went to the admin, none was not met. 11 model calls, 165 seconds.
Since 14 November 2026: a deeper look before the code, and questions only where there is a real doubt.
  • A missing column is looked for, not given up. When the rule names a column its file does not have, or Family 1 did not find a kind of data, program code looks through every file for a column that holds the same kind of data: by how many of the wanted values it holds, by the shape of its values, by its meaning, and last by its name. Each proposal is put to the admin on the requirements card with its evidence and three choices: use it, it is not the same, or I will add the file. Program code decides how strong the support is; a column that is only alike by name is never used without the admin's word.
  • Two programs, written apart. In the first round a second program is written at the same time, without seeing the first. Both run on the same data. Where their results differ and nothing settles it, the admin gets a card “Which result is meant” with the data and both results. The answer becomes part of the requirements. Where they agree, nothing is asked.
  • The Tester does not see the code. It writes its small hostile data sets from the requirements only, and names the property each one checks. A published comparison found that a tester kept apart from the code writes correct tests far more often (87.8 % against 61.0 %).
  • An expectation can be wrong too. When both programs contradict a Tester's expected output in the same way, that expectation is set aside for the admin, instead of failing the code.
  • A fresh program after three repairs. The limit of rounds stays the admin's (10 unless changed). After 3 rounds of repairs on one program, the Coder starts a new program in a new conversation, and again after 3 more: published measurements show that repairing the same program stops paying after two or three attempts.
  • Family 2 is asked too. For a rule that reads the tree, the requirements card shows the joining strategy in use, the rows per level and the rows that were not joined.
Measured with the real model (Model connection, claude-sonnet-5-5, 12 records; the rule says “Duration”, the file has “Minutes”): the first card proposed the column Minutes as the substitute; after the admin's answers no question was left; the two programs agreed; 8 of 8 data sets passed in the first round; 8 model calls, 91 seconds.
What is not trusted. The output a Tester expects for a data set is the Tester's claim. When the code and the claim differ, the Coder corrects the code or objects with a reason; the Tester then withdraws the data set or keeps it. A data set both keep is set aside for the admin to judge, with both reasons. The code is never bent to an expectation without the record saying so.
The chain of thought is kept. For every round the card shows a timeline: the Coder's notes, what changed in the code, each data set with its expected and its actual output, the program's checks and the Tester's notes. The same record is stored in a file beside the code. These are the notes each agent writes of its own work. The model service does not hand out a model's hidden reasoning, and a request that asked for it was refused during the tests; the agents are therefore asked for a work log.

Approve stores it as the verified code of that version of the procedure; Run uses it, and it is never built again while the procedure stays the same. Change, with a comment, is feedback: the rounds start again from the last code. In a flow, each chosen item therefore has two cards of Family 4: the requirements, and the code.

2. Stage 1: identifying the errors

Three families, in order. Each family ends at an admin's review. Family 1 learns each CSV file, giving a data dictionary. It first takes the column meanings that are already known (an approved dictionary, the reference document of the tool that exported the file, an earlier run) and asks the AI model only for the rest. Family 2 joins the five files into one tree by identity keys. Family 3 turns the admin's questions and error definitions into rules, and code finds the errors. AI drafts and explains; it never decides whether an error exists, and it does not name the defect or decide its cause.

A note on names. In the application's own screens, “stage 1” means the isolation of one error's defect, and “stage 2” the procedural graph: its cause and its solution; the test case follows. This page uses the owner's wider framing: Stage 1 is everything up to the errors found; Stage 2 is from each error to its test script.

3. Stage 2: from the error to a test script

Each error is taken through its own page. Code computes the error's evidence card from its own command and decides its cause by fixed rules in a fixed order; the isolation is kept per error. The dictionary names the defect. The procedural graph holds, for each defect, its causes and their solutions. The admin judges stored solutions with one of four signals, and the judgements decide the order shown next time. The admin checks what a correct drive must answer and approves the test. Section 4 says how the defect is named and its cause decided.

4. How a defect is named and classified, and what the model does not do

Two things about a defect must not depend on who looks at it, on which day, or on how much of the recording is on the screen: its name and its cause. Both are fixed by program code, from codes in the recording. The AI model writes words around them; it never chooses them.

The name: four codes from the recording

Code builds each defect's key from codes only, never from words or measured values (terms.defect_term() in nvme_hier/terms.py, dictionary version 3). The key has four parts:

  1. the rule that found the error, for example cmd.timeout;
  2. the command's class and operation code, for example io.read;
  3. what happened to it: aborted by the host, never completed, completed late, slower than usual, or an error status (for any other rule: the rule's own description and the part of the command it concerns);
  4. where the command stopped, as the detector's stage code (for example stage.data), or the official NVMe status code (for example nvme.sc.0.07: status code type 0, status code 07h).

Example: the key cmd.timeout|io.read|aborted_by_the_host|nvme.sc.0.07 is named “Read aborted by the host, status Command Abort Requested”. The status names are the NVM Express Base Specification's, as Linux spells them.

No measured value is ever in a key: no time stamp, row number or duration. On the synthetic S17 recording, the 746 errors found by its two latency rules alone (Time Delta at or above the link limit or the split limit) give 12 keys, so 12 defects, not 746. The whole recording has 775 errors and 23 keys; its 7 command timeouts give 3. (Counted on 11 November with the current code, on a copy of the owner's S17 tree.)

The key is the defect's identity in the procedural graph: it is stored as term:<key> (table dg_defect). The same kind of defect, found by any admin, on any drive, on any day, lands on the same stored defect: storing it again returns the stored one, never a copy. The drive and the firmware are not in the key; they are kept with each occurrence.

Nobody types the name, and the model does not choose it. An admin who thinks an error is not the same kind of defect presses Not the same kind of defect? and writes why; the note goes, with the admin's name, to knowledge/dictionary/term_requests.jsonl for the dictionary's keeper. The name stays as code made it until the dictionary changes. Each name carries the dictionary version it was made with.

A cause is one keyword from a fixed list of 20 (terms.CAUSES), grouped by side:

Code decides the keyword from the error's evidence card (evidence.card()), which it computes from the error's own command, never from the window on the screen: the steps the command reached and their times, the longest wait, the host's Abort of it, its own link problems, and what else ran meanwhile. Then fixed rules, in a fixed order, decide; the first that applies wins (evidence.decide_cause()):

  1. the rule itself is a link event (link down, speed change, electrical idle): link recovery or retraining;
  2. the command's own packets were refused (Nak) or left unacknowledged: replay storm;
  3. a link event happened while the command was outstanding: link recovery or retraining;
  4. the host sent an Abort while it was outstanding: sooner than this command type usually takes in this recording (its median) means a test tool or program aborted it; before the host driver's limit means the host's timer is shorter than the drive's answer time; after the limit means the driver's recovery;
  5. the command never completed: firmware stall;
  6. the completion entry was written, but no interrupt followed: the interrupt never reached the host;
  7. the interrupt came, but the host never took the completion;
  8. the drive answered with a media error status: media retry or read error;
  9. it took longer than this command type's usual time here: a delay inside the drive;
  10. none of these: unknown cause.

So the rules can decide 11 of the 20 keywords. The other 9 (the queue set-up, the power-saving state, interrupt coalescing, garbage collection, thermal throttling, a controller fatal error, waking from ASPM L1, no flow-control credits, and an unanswered or failed PCIe read) are never chosen by the rules today; only an admin can choose them.

So the same card always gives the same cause. The isolation is kept per error (table dg_isolation), under a fingerprint of the card and the versions of the card rules, the dictionary and the model. A bigger or smaller window, or Isolate again, gives the same cause.

The admin uses the decided cause (Use this cause) or picks another keyword from the same list (Use the chosen keyword). The error page has no box for a written cause; it offers only the 20 keywords, and the server refuses a keyword outside the list. (An older route, used by flows made before 11 November, can still store a written line as a cause.) Every change of an error's defect or cause is kept, with the admin's name and the time (table dg_occurrence_log; rows are only added).

5. How the system improves itself

“Recursive self-improvement” has a specific meaning here. Approved dictionaries, strategies, rules, and defects with their causes and solutions are stored, versioned and used again. The meaning of a column, once understood, is kept too and is not looked up again. The admin's corrections change what happens next time. No model is trained or fine-tuned.

The admin's approval gates. Approve stores the work as a new version and moves on. Change runs the step again with the admin's comment. Reject stops the run. Ask questions the agent, without changing the state.

  • The admin confirms each error's cause or picks another of the 20 keywords (fixed rules decide one first), and judges each stored solution with one of four signals.

Every error on the errors page has a button “Isolate this error”. It opens the page of that one error. Parts 1 to 3 show the facts, the commands around the error and the isolation (see section 4 and section 6). First, a story: the garage binder

A car stalls, but only sometimes. The mechanic plugs in the reader and gets the car's log. The car itself writes a code for what happened, for example “stalled in third gear, misfire code”. The mechanic does not invent the name: it is the code, and every garage reads it the same way.

The garage has a binder. In it, each kind of fault has a page. On the page are the possible causes, printed on a list: a mechanic ticks one, he cannot write his own. Under each cause are repair cards. Each card has two lists: “what makes it stall again” and “what fixes it”.

After a repair, the mechanic stamps the card: worked or did not work. Next time, the cards with the best record are at the front. A card with one lucky stamp does not jump ahead of a card with a long good record.

Before the car goes back, the mechanic writes a test drive: “drive this route; the engine must not stall”. He tries it on the practice car, once with the fault and once without. Then he signs it and sends it to the inspection station, which runs it on every car.

Part 4: The cause of this error

The name comes first, and nobody types it. Fixed code builds the defect's name from the recording: the command, what happened to it, and the NVMe status. Everyone gets the same name for the same kind of error. The AI model never chooses it.

The cause is one word from a list of 20. The words are grouped by side: the host (3), the driver or admin software (3), the interrupt path (2), the device (6), the link (3), PCIe transactions (2), plus “not decided from this recording”. Free text is refused.

The fixed rules propose a word. 11 of the 20 words can be decided by the rules from the recording. The other 9 only the admin can choose, because the five exported files do not hold their evidence: queue set-up, the APST power state, interrupt coalescing, garbage collection, thermal throttling, a controller fatal error, waking from ASPM L1, no flow-control credits, and a PCIe read not answered.

Example, row 144. The rules chose “a test tool or program aborted the command on purpose”. Why: the Abort came 60 µs after the doorbell. That is sooner than this command type usually takes here (median 65.775 µs). The host's limit is 30 s, so the host was not out of time. The margin is small: 5.775 µs. A slightly later Abort would have given “the host's timer is shorter than the drive's normal answer time”.

Two buttons, one action. “Use this cause” sends the rules' word. “Use the chosen keyword” sends the word picked in the drop-down. Behind both, the same steps run:

  1. Check that the rule's result was approved first.
  2. Check that the word is one of the 20.
  3. Find the cause under this defect, or create it the first time. Only causes someone chose exist in the binder; until then the 20 words exist only in the dictionary.
  4. Record one count for this error: error → defect → cause, with the drive model and firmware. Rows are only added, never changed.
  5. Copy the rows of the error's command, with 15 commands above and 15 below, into the knowledge base. For row 144 that is 6.72 MB, kept compressed in 1.68 MB. They survive deleting the upload.
  6. Open part 5.

Choosing again for the same error moves its count to the new cause; it is not counted twice.

The grey hint under each word says what evidence would point at it. For example, “packets were resent many times on the link” needs Nak packets and repeated sequence numbers in the window. The window of row 144 has a clean link, so that word would be wrong there.

If nothing fits, choose “not decided from this recording”. Adding a new word needs a change in the code. That is a proposal; it is not built.

Part 5: The solution

A solution is two lists, like the two sides of a repair card:

  • The error sequence: the commands that make the error happen again. Code cuts them from the recording. The error's own step always stays. The test is written from this list.
  • The optimized sequence: what fixes or avoids the problem, one action per line.

If the cause already has stored solutions, they are shown, the best judged first.

If it has none, the AI drafts the optimized lines. It receives the defect's name, the drive, the isolation text, the chosen cause and the error sequence. Its proposal stores nothing. The admin drops steps that are not needed and edits lines. “Store this solution” saves it as version 1, “not yet judged”, and records who made it: “model, stored unchanged by …” or “model, edited by …”.

If stored ones do not fit, “None fits: store this recording's sequence as a new solution” does the same with this recording's sequence.

The four judgement buttons, and how the order changes

The application learns by counting. No AI model is trained.

Two ledgers, never mixed. Judgements order what is shown. Lab counts order what is tried. Neither changes the other.
Honest notes.
  • This is learning from counts. It is not textbook reinforcement learning, and no model is trained.
  • “Correct with my edits” counts as a full correct.
  • Three constants were chosen, not measured: the 95 % level, the cause's lab share being worth 2 runs, and other firmware being worth at most 2 runs. (Two more constants that set the timing brackets of the search were chosen the same way.)

The optional search: the conditions that bring the failure back

Like a mechanic driving the practice car again and again until it stalls, this part replays changed sequences and counts how often the failure comes back.

  • Nothing runs until the admin presses the button.
  • Choose where to replay. Today only the simulated drive. Nothing is pre-selected.
  • Choose a budget of lab runs: 200 by default, from 20 to 5,000.
  • It starts from the stored solution whose failure came back most often, unchanged, with the gaps set at values that worked before.
  • Then it tries changed versions: leave commands out or put them back, reorder only commands that do not depend on each other, change the gaps. Every command and value still comes from the recording.
  • Each try runs 2 times, and 10 times when the failure comes back.
  • A stress step then shortens the gaps while the failure still returns, with up to 90 more runs.

The search writes its run counts back to the graph. It never writes a judgement and never stores a solution by itself. “Store this sequence as a solution of the cause” stays off until a search has finished; pressed, it stores the sequence as a new, not-judged solution.

What a result means. A result on the simulated drive shows that the search works. It never shows that a real drive fails. Without the simulator's time hint, the search found 33 of 50 hidden triggers, against 37 of 50 for a random choice.

Part 6: The test case

  1. “Propose what a correct drive must answer”. The AI suggests the expected answer for each command. For row 144: the Read must end with Success, not Command Abort Requested. The admin corrects what is wrong.
  2. “Write the test file”. Code writes the Python test. It replays the commands one by one and checks each answer.
  3. The two-way check on the simulated drive. The test must fail on a faulty drive and pass on a correct one.
  4. “Approve this test”. The admin's name, the time and a fingerprint of the file are stored. A file changed after approval cannot be handed over.

Part 7: Hand over to the validation suite

  1. Tick a test. Only an approved test whose file has not changed can be ticked.
  2. “Build the package”. A name is required. The result is one zip with the test, the replay library and a README.
  3. “Bring in” the suite's result file (JUnit XML, at most 5 MB). It is recorded with the admin's name. It counts as lab runs of the solution only when the file says which bench ran it, that the run looked for the error, and in how many runs the failure came back. One run is counted once.
  4. “What came back” lists the results brought in.
Watch the library fingerprint. If the replay library changed since the test was written, run the two-way check again before handing the test over.

NVMeNon-Volatile Memory Express, the command language an SSD uses.
CSVComma-separated values: text that opens as a spreadsheet.
Packet, link, split, NVMe transaction, NVMe commandThe five levels of the recording, from the smallest unit to one whole order to the drive.
The tree, the fixed joining strategyThe tree is the five exports of one recording joined into one hierarchy. The fixed joining strategy is the program that joins them; it is an option the admin chooses after stage 1.
REA findingsThe decompiled program of the analyzer, as text files: evidence for how the analyzer itself joins the levels.
REA agentThe agent on the start page that reads the REA findings once and answers questions about them, each answer with its file, lines and quoted words.
Investigation agentA terminal agent of one analysis: it explores the files on request, says what it is doing, and can write a CSV. Its session is kept by name and opened again later.
CompactionWhen a conversation is 95 % of what the model can read, the model writes a summary of it and the conversation goes on from the summary. The full text stays in the application's record.
Substitute columnA column that holds the same kind of data as a column a rule needs but the file does not have, proposed with evidence and accepted or refused by the admin.
DoorbellThe signal by which the computer tells the drive that a new command is waiting.
Completion entryThe drive's message that a command has finished.
Stand-inA built-in program that gives a fixed answer in place of a live AI model, so the application works and can be tested without one.
UploadOne recording loaded into the application.
Error, defectAn error is what a pattern (rule) finds in the recording. It is called a defect only after its isolation.
Evidence cardThe facts code computes from an error's own command: its steps and times, the longest wait, the host's Abort, link problems, what ran meanwhile.
Defect keyThe four codes a defect's identity is made of: the rule, the command's class and operation code, what happened, and the stage code or the NVMe status code. No measured value is in it.
Cause keywordOne of 20 fixed words for a cause, grouped by side, decided by fixed rules from the evidence card.
Model connectionThe part of Settings that decides where every model call goes: the URL, the model name and the API key.
opencodeA terminal program that talks to a model. With it chosen in Settings, the application asks every question through it and calls no model address itself.
Session (terminal session)One conversation of one agent with the model through opencode. It has a name; the application keeps every question and answer of it, and the agent's next question continues it.
Procedural graphWhat is stored for each defect: its causes, and for each cause its solutions with the admin's judgements.
Error sequence, optimized sequenceThe two parts of a solution: the commands that make the error happen again (the test is written from it), and what solves the problem.
